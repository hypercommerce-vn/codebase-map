# Codebase Map

> **Standalone function dependency graph generator** for Python (and TypeScript) projects.
> Output: interactive HTML + JSON. **100% offline · zero CDN.**
> **License:** MIT · **Version:** 2.4.0

Parse your codebase into a function dependency graph (nodes = functions/classes, edges = call relationships). Foundation for understanding large codebases, PR impact analysis, and dual-snapshot diff.

## Quick Start

**No config file?** Run `codebase-map generate` in the project root. It finds the Python and TypeScript/JavaScript sources on its own and skips `node_modules`, build output and virtualenvs. Add a config when you want to choose the folders, name your own domains, or change the output location.

### 1. Create config at project root (optional)

```yaml
# codebase-map.yaml
project: "my-app"
sources:
  - path: "app"
    language: python
    base_module: "app"
    exclude: ["__pycache__", "migrations"]
output:
  dir: "docs/function-map"
  formats: [json, html]
graph:
  depth: 3
  group_by: module
```

### 2. Generate graph

```bash
codebase-map generate -c codebase-map.yaml
```

Output: `docs/function-map/graph.json` + interactive `index.html`.

The config can also be JSON (`codebase-map.json`, same keys), which needs no PyYAML.

### 3. Query the graph

```bash
codebase-map summary -f docs/function-map/graph.json
codebase-map query "CustomerService" -f docs/function-map/graph.json
codebase-map impact "AuthService" -f docs/function-map/graph.json
codebase-map search "create" -f docs/function-map/graph.json
```

### 4. Dual-snapshot diff (v2.2)

```bash
# Create baseline
codebase-map generate --label "baseline"

# ... make changes ...

codebase-map generate --label "post-dev"
codebase-map snapshot-diff --baseline baseline --current post-dev --format markdown
```

The diff reports three levels of change:

| Level | What it catches |
|-------|-----------------|
| Signatures | Functions added, removed, renamed, or with changed parameters, return type, decorators or parent class |
| Function bodies | A function whose code changed while its signature stayed the same |
| Files | Every source file that was added, removed or edited, and whether code outside functions (constants, imports, types) changed |

Body and file changes need both snapshots to be generated by a version that
stores content fingerprints. With an older snapshot the report says that
content is not tracked instead of reporting "no changes".

### 5. Features, acceptance criteria and evidence

A feature is a named part of the product, the files that implement it, and
the acceptance criteria its owner agreed to. They live in one file inside the
project, `.cbm/features.json`.

```bash
# Define a feature: files, folders or globs (* and ?)
codebase-map features add --id booking --name "Booking" \
  --files app/booking app/api/bookings lib/bookings.ts

# Agree on a criterion, then record that it was checked
codebase-map features criterion --feature booking --text "A taken slot cannot be booked twice"
codebase-map features evidence --criterion booking-1 --kind manual --note "Tried it in the browser"

# The application map: features, their screens and endpoints, criterion status
codebase-map features status

# After a change: which features it touches, which criteria to check again
codebase-map features impact --baseline before --current after
```

Every criterion is in one of three states:

| State | Meaning |
|-------|---------|
| `verified` | Evidence exists and the feature's code has not changed since |
| `needs_recheck` | Evidence exists, but code the feature owns or depends on has changed |
| `unchecked` | No evidence yet |

A feature **owns** what its patterns match and **depends on** what that code
calls, plus the constants and other top-level code of the files involved.
Evidence stores a fingerprint of all of it; reformatting, imports and type
declarations do not change the fingerprint, any edit that can change
behaviour does. `features impact` reports a feature as touched `direct`ly
(its own files were edited) or `indirect`ly (code it depends on was).

The tool never says a criterion is met. It says whether evidence exists and
whether the code has changed since. All `features` commands take `--json`.

Limits: a dependency that exists only at run time is not seen — a screen
calling an endpoint through `fetch("/api/…")`, or two features sharing a
database table. List the endpoint's file under the feature that uses it.

## Commands

| Command | Purpose |
|---------|---------|
| `generate` | Generate function dependency graph |
| `query` | Look up function/class details |
| `impact` | Show impact zone for a node |
| `search` | Search nodes by keyword |
| `summary` | Graph statistics |
| `diff` | Git diff impact analysis |
| `snapshot-diff` | Dual-snapshot diff: signatures, function bodies, files |
| `snapshots` | Manage snapshots (list/clean) |
| `features` | Features, acceptance criteria and evidence; impact of a change on them |
| `api-catalog` | List API routes |
| `coverage` | Overlay test coverage |
| `check-staleness` | Check graph freshness |

All commands support `--help` for detailed options.

## Features

### 🔍 Graph Generation
- Python AST parser (classes, functions, methods, decorators)
- Layer classification (route / service / model / util / schema / test)
- Domain clustering (by module path)
- Call graph edges + import edges
- JSON + interactive HTML output

### 📊 Dual-Snapshot Diff (v2.2)
- Compare two graph snapshots (before/after)
- Added / removed / modified / renamed functions
- Affected callers (transitive, 1-3 levels)
- Rename detection via signature matching
- Output formats: markdown (PR body), JSON (CI), text (terminal)

### 🎨 Interactive HTML
- D3.js force-directed graph (bundled, offline)
- Sidebar tree, minimap, toolbar
- Executive view, PR Diff view, API Catalog
- Multi-view tabs, breadcrumb navigation
- Business Flow mapping

### ⚙️ CI Integration
- `cbm-baseline.yml` — auto-baseline on merge to main
- `cbm-post-merge.yml` — rotate baseline after PR merge
- `cbm-pr-impact.yml` — post PR Impact comment (dual-snapshot)

## Architecture

```
Source Code (Python/TS)
    ↓
  [AST Parser]
    ↓
  [Graph Builder]  → Nodes + Edges + Metadata
    ↓
  [Exporters]      → JSON + HTML (D3.js)
    ↓
  [Query Engine]   → summary, impact, search, query
    ↓
  [Snapshot Diff]  → add/remove/modify/rename + affected callers
```

CBM is **stateless**: every command takes graph.json as input. No database, no state.

## Use Cases

### Before modifying a function
```bash
codebase-map impact "CustomerService.create" -f graph.json
# Shows all callers — know blast radius before refactoring
```

### In PR description
```bash
codebase-map snapshot-diff --baseline main --current feature-branch --format markdown
# Copy-paste into PR body — reviewers see structural impact
```

### CI auto-comment
Installed workflows post impact analysis on every PR automatically.

### Understand a new codebase
```bash
codebase-map summary -f graph.json       # How big is it?
codebase-map api-catalog -f graph.json    # What APIs exist?
codebase-map query "main" -f graph.json   # Where's the entry point?
```
